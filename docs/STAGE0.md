# Этап 0 — CLI `srmod` на источнике `.rsm`

Пересборка плана после разбора RScript 4.14f и `rsmc` (2026-07-31). Отменяет
раскладку и конвейер из прежнего плана «источник = JSON-`rson`»; всё, что здесь
не оговорено, остаётся как было.

**Суть перемены.** Источник мода — текстовый `.rsm` (UTF-8, кириллица как есть,
git-diff, модули), собирается автономным `rsmc.exe`. Из конвейера уходят два
шага, которые раньше делали мы: слияние сгенерированной секции `Script` в
`Lang` и ре-ключевание CT-текстов — это делает сам `rsmc`. `RScript.exe` в
основной ветке сборки больше не участвует (нужен только для импорта чужих
модов и для запасной rson-ветки), а вместе с ним уходит и `_dlgwatch`: `rsmc` —
обычная консольная программа без модальных окон.

---

## (а) Раскладка папки мода — src/build (переработано 2026-08-04)

По решению юзера (целевой UX модкита): **исходники целиком в `src/`, сборка
целиком в `build/`** — game-ready дерево без исходников и комментариев,
которое ставится в игру junction'ом (`srmod deploy`). `build/` каждый раз
собирается с нуля (осиротевших артефактов от переименований не бывает),
`.gitignore` мода схлопывается до `/build/` и `/.srmod/`.

```
MyMod/
  srmod.json                      имя, install-путь, языки, точка входа, опции
  .gitignore                      /build/  /.srmod/
  src/                            ВСЁ, что пишет автор
    ModuleInfo.txt                UTF-16LE BOM; копируется в build/ как есть
    CFG/
      Main.txt                    → build/CFG/Main.dat
      Rus/ Lang.txt + *.txt       → build/CFG/Rus/Lang.dat  (секции Script в исходнике НЕТ)
    DATA/
      Script/
        MyMod.src/                модули .rsm — единственный источник скрипта
          main.rsm                scriptName(...) + import from './*.rsm'
          vars.rsm world.rsm states.rsm dialogs.rsm code.rsm ...
        (или MyMod.rsm)           односкриптовый вариант
      Items/ hull.png             → build/DATA/Items/hull.gi
             hull.gai.src/        → build/DATA/Items/hull.gai
      Panels.pkg.src/             → build/DATA/Panels.pkg
      прочие файлы                → копируются в build/ как есть (звуки и т.п.)
  build/                          генерится сборкой, руками не трогать:
    ModuleInfo.txt  CFG/*.dat  DATA/Script/MyMod.scr+.txt  медиа  INSTALL.TXT
  .srmod/state.json               хэши src/ для watch
```

Не копируются в `build/`: `*.rsm`, `*.png`, `*.rson`, `CFG/**/*.txt`
(компилируются в артефакты с другим расширением) и любые папки `*.src/`.
Датники и `.rsm` могут нести комментарии `//` и `/* */` — BlockParEditor и
rsmc вырезают их при компиляции (round-trip проверен); единственное
исключение — комментарии в телах `function(){}`: движок хранит код текстом,
они доезжают до `.scr` (как и у всех реальных модов). В `ModuleInfo.txt`
комментарии ЗАПРЕЩЕНЫ — он не компилируется, а копируется.

**Почему модули в `MyMod.src/`, а не россыпью в `DATA/Script/`.** Имена, которые
даёт `RScript --cli -x --split`, безличные (`main/vars/world/places/states/
dialogs/code_*.rsm`) — два скрипта в одном моде затёрли бы друг друга. Суффикс
`.src` у папки-исходника — та же конвенция, что у `*.gai.src/` и `*.pkg.src/`.

Историческая раскладка «источник и артефакт рядом» (до 2026-08-04) выглядела
так и отменена вместе со своим плоским `.gitignore`:

```
*.scr
*.dat
*.gi
*.gai
*.hai
*.pkg
DATA/Script/*.txt
CFG/CacheData.txt
INSTALL.TXT
.srmod/
```

**Односкриптовый вариант разрешён:** если `MyMod.src/` нет, точкой входа
считается `src/DATA/Script/MyMod.rsm` (одним файлом, без `import`). Порядок
поиска входа: `srmod.json:script.entry` (путь от корня мода) →
`src/DATA/Script/<name>.src/main.rsm` → `src/DATA/Script/<name>.rsm`.
Проверено: имя точки входа `rsmc` безразлично (`MyMod.rsm` вместо `main.rsm`
собирается так же), `import from './…'` разрешается относительно каталога
точки входа, одиночный файл без `import` собирается.

**Что НЕ кладётся в git:** весь `/build/` и `/.srmod/`. Сохранённый импортом
`<Name>.import.rson` лежит в `src/DATA/Script/` (нужен `verify --gate`), в
`build/` не копируется.

**Кодировки (гейт сборки, не рекомендация):** `ModuleInfo.txt` и все исходные
`*.txt` для датников — **UTF-16LE + BOM** (в git читаемо через
`.gitattributes` `working-tree-encoding=UTF-16LE-BOM`); `.rsm` — **UTF-8**.
BlockParEditor молча портит UTF-8 на входе («РџСЂРёРІРµС‚», ноль ошибок),
поэтому `srmod build` обязан проверять кодировку входных `.txt` и падать.

## (б) Конвейер `srmod build`

Порядок обязателен: язык готовится ДО вызова `rsmc`, потому что `rsmc` мержит
тексты в уже существующий файл.

| # | Шаг | Чем |
|---|---|---|
| 0 | `build/` сносится и создаётся заново; статика `src/**` → `build/**` (всё, кроме `*.rsm`/`*.png`/`*.rson`/`CFG/**/*.txt`/папок `*.src/`) | свой код |
| 1 | Медиа: `png→gi`, `*.gai.src/→gai`, `*.hai.src/→hai` — `src/DATA/**` → `build/DATA/**` (то же отн. место) | `srgi.py` из rson-decompiler |
| 2 | Стейджинг языка: `src/CFG/<lang>/*.txt` → **временный** файл; в файл основного языка добавляется каркас `Script ^{ <scriptName> ^{ } }`, если его там нет (проверка «есть ли блок» — по тексту без комментариев!) | свой код |
| 3 | Скрипт: `rsmc build <entry> -o build/DATA/Script/<Name>.scr --lang-txt <врем. Lang.txt>` | `rsmc.exe` |
| 4 | `<врем. Lang.txt>` → `build/CFG/<lang>/Lang.dat`; неосновные языки — из своих исходников как есть | свой код (`vendor/srblockpar`) |
| 5 | `src/CFG/Main.txt` → `build/CFG/Main.dat`; **гейт**: в Main.txt обязана быть связка `<Name>=1,Script.<Name>` (см. ниже) | свой код (`vendor/srblockpar`) |
| 6 | Генерация `CacheData.txt` из `install`-пути → `build/CFG/CacheData.dat` | свой код |
| 7 | `src/**/X.pkg.src/` → staging (медиа кодируются прямо в staging, без `png`/`times.json`) → `build/**/X.pkg` + генерация `build/INSTALL.TXT` | `srpkg.py` |
| 8 | (опц. `--deploy` / `srmod deploy`) junction `<игра>\<install>` → `build/` — junction переживает пересборку (rmtree+mkdir по тому же пути) | свой код |

Исходный `Lang.txt` на диске не трогаем никогда: `rsmc` пишет в свою копию,
из неё же родится `.dat`. Инкрементальность и `srmod watch` — по хэшам
исходников в `.srmod/state.json`.

**Main.txt обязан подключать скрипт** (сверено по Main.dat реальных модов —
AdvancedOptions, AMod_HardSkills, AMod_Invaders, AMod_DefStation, у всех
одинаково; без этой связки мод виден в списке, но скрипт не стартует — тихо):

```
Data ^{
    Script ^{
        <Name>=1,Script.<Name>
    }
}
```

`srmod new` генерирует её сам, `srmod build` падает, если связки нет
(2026-08-04; корневой блок — `^{`, не `~{`, как в дампах BPE).

### Поведение `rsmc`, проверенное руками (иначе мод уедет к игрокам немым)

1. **`rsmc` всегда пишет `<стем -o>.txt`** рядом с `.scr` — ту же таблицу
   `ключ=текст`, что RScript писал третьим аргументом (UTF-16LE + BOM).
   ⇒ `--lang-txt` **не должен указывать на файл с тем же стемом, что `-o`**:
   таблица затрёт язык до слияния, и вместо мода получится «warning: … has no
   existing Script^{…} block». Именно поэтому временный `Lang.txt` живёт в
   `.srmod/tmp/`, а не рядом с `.scr`.
2. **`--lang-txt` мержит только в уже существующий блок**
   `Script ^{ <scriptName> ^{ … } }`. Пустого каркаса достаточно. Если блока
   нет — `warning` и **`rc = 0`**: сборка «успешна», мод молчит.
   ⇒ шаг 2 конвейера обязателен, а `srmod` обязан **считать `warning:` в выводе
   `rsmc` ошибкой сборки**.
2a. **Код возврата `rsmc`: `error:` даёт `rc = 8`, `warning:` — `rc = 0`.**
   (Перепроверено 2026-08-04 из Git Bash и PowerShell: несуществующий каталог
   у `-o` — `error: TFileEC.CreateNew…`, rc=8; parse error — тоже 8; прежняя
   запись «rc=0 даже на error» не подтвердилась.) Опасны именно warning'и:
   сборка «успешна», а мод без текстов. ⇒ контроль — разбор stdout на
   `error:`/`warning:` плюс rc и проверка, что `.scr` создан и свежее запуска.
   Каталоги под артефакты `srmod` создаёт сам.
3. **Кодировку целевого файла `rsmc` сохраняет:** cp1251 → cp1251,
   UTF-16LE+BOM → UTF-16LE+BOM, кириллица не портится. Правило «исходники
   датников только в UTF-16LE BOM» остаётся в силе и после переезда.
4. **`--lang-dat` умеет мержить прямо в `.dat`** — проверено на реальном
   `AdvancedArts/CFG/Rus/Lang.dat`: блок `Script^{AdvancedArts}` перезаписан,
   соседняя секция `Artefacts` цела, объём тот же, BlockParEditor 1.9 читает
   результат. Оставляем как опцию (`lang.merge_into: dat`) для модов без
   текстового исходника языка; **основной путь — `--lang-txt`**, чтобы `.dat`
   всегда рождался из BPE и оставался ровно одной зависимости шире.
5. **`scriptName("…")` в `main.rsm` — ключ ко всему:** это и имя блока в
   `Lang`, и префикс CT-ключей (`Script.<Name>.N`), и то, с чем `rsmc` ищет
   блок для слияния. `srmod build` сверяет `scriptName` с `srmod.json:name` и
   с именем выходного `.scr` и падает при расхождении.
6. **`DText(...)` в теле `code:` у `dialogMsg`: rsmc не выбрасывает его, но
   молча меняет семантику** (финальная версия 2026-08-04, сверено побайтово по
   `.scr` и подтверждено `RScript --cli -d` обеих сборок на
   `Cat_AsteroidStations`; две прежние формулировки — «выбрасывается» и
   «сохраняется как есть» — обе неточны):
   - строковый литерал внутри `CT("Script.X.N")` rsmc перекеивает как ТЕКСТ:
     в его таблице появляется запись `M=Script.X.N` (строка-ключ как текст!),
     а вызов становится `DText(CT(CT("Script.X.M")))` — двойной лукап;
   - из поля `text:` (даже пустого `""`) rsmc генерит СВОЙ `DText(CT(...))`
     первым оператором кода — итого лишняя пустая реплика;
   - в рантайме двойной лукап случайно работает: внутренний `CT` возвращает
     строку-ключ, внешний резолвит её в оригинальный текст из Lang.dat мода.
     Но только пока таблицу rsmc НЕ мержат в ту же секцию `Script^{X^{}}`:
     merge перетирает оригинальные ключи 0..K строками-ключами и тексты
     превращаются в «Script.X.NN» на экране.
   Практический вывод: для авторских модов текст живёт только в `text:`
   (`srmod lint` это ловит); импортированные моды с `DText(CT(...))` в коде —
   собирать rson-веткой; сверки сборок делать после склейки переносов строк
   (наш `decompiler.py` от переноса кладёт этот `DText` то в код, то в поле
   сообщения).
7. **`ChangeState(<число>)` разрешается по ИМЕНИ, а не по индексу, если в моде
   есть состояние с таким именем.** Найдено корпусным прогоном на
   `Mod_RevDiplomat`: у мода есть состояния с именами `01`, `1`, `20`;
   исходный `ChangeState(1)` (индекс 1) после `rsmc` превратился в
   `ChangeState(7)` — это индекс состояния, которое НАЗЫВАЕТСЯ `1`.
   ⇒ `srmod lint`: запрещать имена деклараций, состоящие из одних цифр;
   `srmod new` такие имена не генерирует.

### Многоязычность

Сгенерированная секция `Script` уходит только в основной язык
(`primary_lang`). Для остальных автор ведёт свой фрагмент руками с той же
нумерацией ключей — ограничение формата, обойти нечем. `srmod build` после
сборки сверяет наборы ключей всех языков и печатает недостающие.

## (в) `srmod.json` и трёхуровневый конфиг

Хардкода путей нет нигде. Три уровня, каждый следующий перебивает предыдущий:

**1. Машинный — `%APPDATA%\srmod\config.json`** (пути к чужим бинарникам):

```jsonc
{
  "tools": {
    "rsmc":     "C:/claude_sandbox/rson_decompiler/rsmc/rsmc.exe",
    "rscript":  "C:/claude_sandbox/rson_decompiler/RScript_4.14f/RScript.exe",
    "blockpar": "C:/claude_sandbox/rson_decompiler/BlockParEditor_1.9/BlockParEditor.exe",
    "game":     "C:/claude_sandbox/rson_decompiler/Space Rangers HD A War Apart",
    "decompiler": "C:/claude_sandbox/rson-decompiler"   // откуда импортировать srgi/srpkg/run
  }
}
```

Автодетект, если файла нет: сиблинги `../rson-decompiler`, `../rson_decompiler`
(как в `tools/build_lexicon.py`), внутри них — `rsmc/rsmc.exe`,
`RScript_4.14f/RScript.exe`, `BlockParEditor_1.9/BlockParEditor.exe`.

**Бандлить эти три бинарника нельзя** — ни у `RScript`/`rsmc`, ни у
`BlockParEditor`, ни у `RangersViewer`/`Cassandra` нет лицензии, а `srmod`
живёт под GPL v3. В репозитории — только пути в конфиге и понятная ошибка
«не найдено, укажи путь» + ссылка на релизы автора. Windows-only, как и раньше.

**2. Проектный — `srmod.json`** рядом с модом:

```jsonc
{
  "name": "MyMod",                       // == scriptName в main.rsm == имя .scr
  "install": "Mods/Artem/MyMod",         // путь от корня игры; от него зависят
                                         // CacheData.dat и INSTALL.TXT
  "languages": ["Rus", "Eng"],
  "primary_lang": "Rus",
  "script": {
    "engine": "rsmc",                    // rsmc | rson  (см. (г))
    "entry": "DATA/Script/MyMod.src/main.rsm"
  },
  "lang": { "merge_into": "txt" },       // txt (по умолчанию) | dat
  "media": { "gi_format": "argb", "gai_format": "delta" },
  "packages": ["DATA/Panels.pkg.src"],
  "deploy": { "mode": "junction" }       // junction | copy | off
}
```

**3. Поверх — флаги CLI и переменные `SRMOD_*`** (`SRMOD_RSMC`,
`SRMOD_RSCRIPT`, `SRMOD_BLOCKPAR`, `SRMOD_GAME`).

`srmod doctor` печатает, что откуда взялось: путь, уровень конфига, версию/пробу
(`rsmc build` без аргументов, проба RScript на `--split`/`--langdat` = 4.14f+,
наличие BPE и какой именно — 1.9 пишет `dat→txt` в cp1251, 2.0 в UTF-16LE+BOM),
и валидацию кодировок исходников мода.

Команды этапа 0: `srmod new` (скаффолд по раскладке выше), `build`, `watch`,
`doctor`, `lint`, `import`, `verify --gate`.

## (г) Запасная rson-ветка и гейт доверия

`rsmc` закрытый (исходники автор обещает после переписи на C++), поэтому
rson-ветка сборки остаётся в коде, а не в истории:

- `srmod build --engine rson` собирает из `DATA/Script/<Name>.rson` штатным
  RScript (`--cli -b <rson> <scr> <txt> --full` для 4.14f+, старая форма
  `-b -f` для ≤4.13f — выбор формы уже реализован в `run.py::_rscript_build_args`),
  через `_dlgwatch` (модалки), и слияние секции `Script` в язык делаем сами —
  прежний конвейер целиком.
- `srmod import <mod.rson>` — `RScript --cli -x … --split` в `<Name>.src/`.
  При импорте печатать предупреждение о классе (б).6: мод, чьи тексты хранятся
  в `Lang` и подставляются `DText(CT("Script.X.N"))`, после `rsmc` получает
  двойной `CT(CT(...))` + лишний пустой `DText`, а merge языка перетёр бы
  оригинальные ключи. Пока `rsmc` это не чинит — импортированные моды с таким
  шаблоном собирать rson-веткой.
- `srmod verify --gate` — сборка обеими ветками и сравнение: сначала байты,
  при расхождении — декомпиляция обеих сборок нашим `decompiler.py` и сравнение
  структур с тремя уровнями нормализации (токены `Code`; схлопывание отступов;
  синтетические `Pos.*`, которых в `.scr` нет). Реализация и корпусный прогон —
  `rson_decompiler/_rsm_regress.py`, отчёт `_rsm_regress_out/REPORT.md`.

Гейт зелёный ⇒ можно жить на `rsmc`; красный на конкретном моде ⇒ этот мод
собирается rson-веткой, а расхождение уходит в issue автору `rsmc`.

### Результат корпусного прогона (2026-07-31)

Корпус: `decompile_result/` (330 rson) + `rsons/` — **539 файлов**, из них
компилируются штатным RScript 530. Прогон:
`python _rsm_regress.py` (≈10 мин, ~1 с на мод), отчёт —
`rson_decompiler/_rsm_regress_out/REPORT.md`.

**Гейт: 523/530 (98,7 %) сборок `rsmc` эквивалентны сборке RScript.**
(Прогонщик даёт 521: два его «расхождения» — `Cat_AsteroidStations` и
`PC_fem_rangers_` — сняты перепроверкой инструментами автора, см. (б).6.)

| Итог | Файлов |
|---|---|
| байт-в-байт | 172 |
| rson-декомпиляция обеих сборок идентична | 158 |
| совпало после нормализации кода (`-x` схлопывает `if(){}` в строку) | 11 |
| совпало после схлопывания отступов (rsmc пишет тело с отступом) | 71 |

Из 3 расхождений после перепроверки инструментами автора остаётся **одно

строки, которую наш декомпилятор показывает как перенос `DText` (пункт (б).6);
`RScript --cli -d` на обеих сборках даёт одинаковый текст.

Все 6 несобравшихся — семейство `PC_final` из установленных модов: в коде
ответа диалога **на одну `{` больше, чем `}`** (`if(flagvar==0) {` закрыт не
до конца). RScript такой код принимает, парсер `rsmc` — нет
(`dialogs.rsm(line=…, symbol=3): expected "}"`). Воспроизводится целиком на
инструментах автора: `RScript --cli -d` шиппящегося
`Mods/Reflection/RefAltStartOnlyPirates/DATA/Script/PC_final.scr` → `--cli -x
--split` → `rsmc build` = ошибка, при том что `--cli -b` того же `.rson`
собирается без единого замечания.

Нормализации, которыми пришлось обвесить сравнение (иначе шум топит сигнал),
сами по себе — список того, чем `.rsm`-сборка законно отличается от rson-сборки:
номера CT-ключей у компиляторов свои (сравнивать надо тексты, но **только по
своей секции** — `CT('Script.PC_final.186')` в чужую таблицу лезть нельзя),
имена одноимённых деклараций `-x` разводит, координаты узлов в `.scr` не
хранятся вовсе.

## (д) Этап C — `srmod open`: любой компилированный мод -> проект src/ (2026-08-04)

`srmod open <папка-мода> <dest> [--name X] [--install Mods/...] [--pkg-limit MB]
[--verify]` — один проход: скрипт, датники, медиа и pkg разбираются в исходники,
генерируются `srmod.json` и `.gitignore`. `--verify` (или отдельно
`srmod verify --rebuild <папка-оригинала>`) сразу собирает проект и сверяет
`build/` с оригиналом — гейт пересборки.

**Принцип: декомпилируется только то, что воспроизводится без потерь.**
Каждый медиа-файл проверяется round-trip'ом (decode -> encode == оригинал
побайтово); проигравшие остаются бинарниками в src/ как есть. Тот же принцип
для скрипта: `.rsm`-ветка принимается только если rsmc-сборка из экспорта
эквивалентна оригинальному `.scr` (сравнение с CT-разрешением) — иначе
`script.engine=scr` (бинарный passthrough, тексты остаются в Lang.txt),
а модули `.src/` лежат справочно.

### Что куда разбирается

| Оригинал | Исходник | Чем |
|---|---|---|
| `DATA/Script/<N>.scr` | `<N>.import.rson` + `<N>.src/*.rsm` | каскад: наш decompiler.py (FileVersion 7/8) -> `run.py rsdec` (RScript `-d`, старые форматы) -> engine=scr |
| `CFG/Main.dat`, `CFG/<L>/Lang.dat` | `Main.txt`, `<L>/Lang.txt` (UTF-16LE BOM) | BlockParEditor dat->txt |
| `CFG/CacheData.dat` | `CFG/CacheData.txt` без секции Script, префикс установки заменён на `$INSTALL$` | BPE + свой код |
| `*.gi` | `<stem>.png` (+ сайдкар `<stem>.gi.json {"format": ...}`, если формат не argb) | srgi in-process; формат подбирается по `type=` заголовка |
| `*.gai/*.hai` (<= 2 МБ) | `<stem>.gai.src/` кадры (+ сайдкар формата) | srgi CLI; больше лимита — бинарник (encode_delta 200-кадрового gai — минуты чистого python) |
| `*.pkg` (<= `--pkg-limit`, дефолт 64 МБ) | `<stem>.pkg.src/` + внутренние медиа тем же способом | srpkg; DenBG.pkg на 1.6 ГБ остаётся архивом |
| нативные `.png` (игра читает png, в т.ч. из pkg — SR2RebootMenu!) | копия + сайдкар `<stem>.png.json {"raw": true}` | build такой png копирует, а НЕ кодирует в .gi |
| `INSTALL.TXT`, `DATA/Script/<N>.txt`, таблицы CT где угодно (детект: `<name>.txt` из одних `N=`-строк, напр. `CFG/Rus/AdvancedOptions.txt`) | не переносятся — артефакты | build/rsmc воспроизводят |

`srmod.json` дополнен: `script.engine: rsmc|scr|none` (none — мод без скрипта,
напр. чисто медийный), `install_txt: false`, если оригинал не шипил INSTALL.TXT
(SR2RebootMenu держит INSTALL_RUSSIAN/ENGLISH.TXT на выбор игрока).

### CacheData — реверс по корпусу (385 модов, закрыт 2026-08-04)

Секции `Bm`(246)/`Script`(236)/`Sound`(35)/`ABMap`(4)/`Graphicks`(2)/`Font`(2);
все — плоский резольвер «внутренний ключ ресурса -> путь»: путь от корня игры
к файлу мода (7560 значений), VFS-путь внутрь pkg (1816; pkg монтируется в
корень VFS, потому и `data\Items\...` работает), редко — путь от корня мода
(20). **Ключи семантические** (имена предметов/кораблей/фонов из данных игры)
— из файлов их не вывести, автогенерация невозможна И не нужна: файл шиппится
автором (mtime старше установки), а не генерится игрой. Поэтому `srmod build`
подставляет `$INSTALL$` в сохранённый исходник и ставит сгенерированную секцию
`Script` первой (грабля BPE 1.9 про порядок на корне остаётся в силе). Секция
Script в исходнике запрещена (гейт).

**Ключ записи ≠ имя скрипта** (Cat_Tardis: `Tardis=…\cat_tardis.scr`,
SR2Dominators: `MS_Begin_Legacy=…\MS_Begin.scr`), поэтому «своя ли запись»
решается по ЗНАЧЕНИЮ: путь внутри каталога установки + имя файла из наших
скриптов (`opener._points_at_own_scr`). Фильтр по ключу оставлял такую запись
в исходнике, а build генерил её же — и гейт ронял сборку. Записи на скрипты
вне каталога установки — авторские (Den_DatVersion переопределяет `ms_begin`
и прочие скрипты самой игры), они сохраняются как есть.

Смежная находка: `Rangers.exe savemergedcfg` (см. `GenerateMergedCFG.bat` в
корне игры) дампит СМЁРЖЕННЫЕ CFG/Lang/Main/CacheData всех модов в корень игры
— пригодно как гейт уровня игры и как справочник финального вида секций.

### Гейт пересборки `verify --rebuild`

- `.scr`: байты -> структура без шапки/Pos.* -> схлопнутые пробелы ->
  CT-ключи разрешены в тексты через таблицу СВОЕЙ сборки (у rsmc нумерация
  своя; таблица оригинала берётся из Lang.dat, файла-таблицы может не быть).
- `.dat`: оба -> текст (BPE) -> построчно; `CacheData.dat` — без регистра и
  порядка корневых секций; `Lang.dat` — секция `Script^{<name>}` мягко, если
  `.scr` сошёлся (rsmc переномеровывает согласованно). Если построчно не
  сошлось — сравнение по канонической структуре (`canon_blockpar`): **порядок
  вложенных блоков BPE не сохраняет** — тот же текст, записанный заново,
  читается назад с другим порядком (Den_UIRecolor: у оригинала `Bm` начинается
  с `formnote`, у пересборки с `cformbg`), а игра читает датник как словарь.
- Таблицы CT и INSTALL.TXT-варианты — инфо-статусы, остальное — байты.

### Мультискриптовые моды (сделано 2026-08-28)

28 из 236 скриптовых модов везут по 2–9 `.scr`. В `srmod.json` появился список
`scripts: [{name, engine, entry, cache}]` (без него мод описывается прежней
парой `name` + `script`), `srmod open` заполняет его сам, `build` крутит цикл:
свой вызов rsmc на скрипт, свой каркас `Script^{}` в staged-Lang, своя строка в
`CacheData`. Проверено на BlockSOTE (2), ExpTraitors (3), RefGreeting (6),
KavkazScripts (9 — смешанные движки) — все четыре MATCH.

Что выяснилось по дороге (всё — факты корпуса, не правила):

- **Основной скрипт определяется по `Main.dat`**, а не по имени каталога:
  вспомогательные `.scr` там не упомянуты вовсе (RefGreeting — 6 скриптов, в
  Main один). Гейт связки требует основной скрипт и только его.
- **Ключ связки ≠ имя скрипта**: у AMod_Merchant `mod_trader=1,Script.mod_merchant`.
  Проверяем только правую часть `Script.<name>`.
- **Попадание в `CacheData` — авторское решение**: у BlockSOTE в секции Script
  оба скрипта, у RefGreeting из шести — один. Отсюда поле `cache` у скрипта.
- **Каркас `Script^{}` кладётся ВНУТРЬ существующего блока**, если он есть:
  второй корневой блок с тем же именем даёт `.dat`, который BPE потом не читает
  назад (KavkazScripts, «no output written»).

### Ещё две грабли BlockParEditor 1.9 (найдены корпусным прогоном 2026-08-28)

- **Имя `CacheData` включает в BPE особый режим.** Если имя входного `.txt`
  ИЛИ выходного `.dat` — `CacheData`, редактор требует в тексте секцию
  `Script`; не найдя её, пишет ПУСТОЙ `.dat` (8 байт) без ошибки и без диалога.
  Мод Den_DatVersion (в CacheData только `BV^{}`) собирался в мусор. Лечение —
  `run_blockpar` всегда конвертирует во временном каталоге под нейтральным
  именем `srmod_bp` и копирует результат на место.
- **INSTALL.TXT не всегда выводится из списка пакетов.** Den_UIRecolor везёт три
  `.pkg`, а в INSTALL.TXT вписан один (языковые монтируются иначе). `open`
  сверяет список с пакетами мода и, если они разошлись, переносит файл в `src/`
  как есть (`install_txt: false`); генерация — только когда список полный.
- **`//` внутри значения не переживает текстовый round-trip.** BlockPar считает
  это началом комментария и обрезает значение — одинаково в 1.9 и 2.0, то есть
  это правило формата, а не баг версии: `WeRunOnWine=…https://www.protondb.com…`
  превращается в `…https:`. Такой `.dat` остаётся бинарным исходником (как
  медиа, чей round-trip не сошёлся), а если это `Lang.dat`, то и скрипт мода
  собирается веткой `engine=scr` — rsmc мержит свою таблицу только в текстовый
  Lang. В корпусе так устроен Den_DatVersion (обновлённые датники самой игры).
- **Не всякий `.dat` — датник BlockPar.** У EvoMusic это `DATA/Music/*.dat`,
  BPE его не читает; такие файлы едут копией и сверяются байтами.
- **Секция Script в CacheData бывает и про ЧУЖИЕ скрипты.** Den_DatVersion
  переопределяет скрипты самой игры (`ms_begin`, `ms_blazer`…). Записи о своих
  скриптах генерирует build (пути зависят от install), чужие сохраняются в
  `src/CFG/CacheData.txt` и сливаются с ними в ОДИН блок. Проверка «своя запись
  в исходнике запрещена» смотрит ТОЛЬКО секцию Script: имя скрипта бывает
  ключом и в других секциях (Cat_Dragon: `Dragon=…\Ship\Dragon.hai` в `Bm`).

### Что ещё вылезло на полном корпусе (551 мод, 2026-08-28/29)

- **Медиа лежат не только в `DATA/`.** У семейства PlanetaryBattles картинки в
  собственном корневом каталоге `matrix/`; обход только `DATA/` терял их молча
  (`.png` как есть не копируется — его положено кодировать). `run_media` теперь
  обходит всё дерево мода.
- **UTF-8 у копируемых `.txt` — не наше дело.** Гейт кодировки оставлен только
  для датников, которые компилируем сами; у 25 модов (PlanetaryBattles,
  FairansVision, Tweaks/German) рядом лежат авторские `.txt` в UTF-8, игра их
  читает, и падать на них — значит не уметь пересобрать четверть корпуса.
  Теперь про такие файлы печатается замечание, а сборка идёт.
- **`X.gi` и нативный `X.png` в одной папке** (TicTacToe: `bg.gi` + `bg.png`) —
  декодировать gi некуда, исходником стал бы тот же файл. Такой `.gi` остаётся
  бинарником.
- **Мод может быть собран без связки в `Main.dat`** (RefQuest — скрипт
  запускает кто-то другой). `open` ставит `script.main_link: false`, и гейт
  связки для этого проекта выключается: наше дело воспроизвести мод, а не
  чинить чужой.
- **Таблица CT-ключей рядом со скриптом — артефакт только на ветке rsmc.**
  `DATA/Script/<Name>.txt` пишет сам rsmc при сборке, поэтому у `engine=rsmc`
  её в `src/` не переносим. Но скрипт, оставшийся бинарником (`engine=scr`),
  ничего не пишет — там тот же файл обязан доехать до `build` копией, иначе
  пересборка теряет файл оригинала (FairanBalance, RevolutionDelayed,
  TechnicalIssuesFixer). Решение отложено до момента, когда ветка скрипта
  известна (`opener.deferred_ct`).
- **Нет `CFG/CacheData.dat` — не генерировать его.** У RefLitRes скрипт
  запускает соседний мод, своего CacheData у него нет; `open` ставит
  `script.cache: false`, иначе сборка добавляет файл, которого в моде не было.

**Итог прогона `srmod open --verify` по всем 551 моду: 550 MATCH.**
Единственный не-MATCH — `Mods\SrmodHello`, и это не мод: туда старым
копированием уехала папка нашего же проекта вместе с `srmod.json` и
исходниками `.rsm`, которые сборка (правильно) в `build` не кладёт.

### Почему диалоговые моды остаются бинарником (issue 8, 2026-08-29)

Главная причина фолбэка `engine=scr` — подстановки в тексте реплики. rsmc
собирает `DText(Format(CT(key),"<0>",0,"<1>",1))`: на месте подставляемых
значений стоят номера самих подстановок, а задать переменные в `.rsm` нечем —
`command` уходит в имя узла, явный `DText(Format(...))` в `code` пропадает из
кода, оставляя свои строки в таблице текстов. Минимальное репро и разбор —
`docs/rsmc-upstream-issues.md`, issue 8. Пока не починено у автора, такие моды
воспроизводятся только готовым `.scr`.

### Мультиязычные моды при engine=rsmc (сделано 2026-08-28)

Связь перевода с репликой в этом формате только по номеру ключа, а номера rsmc
раздаёт заново — поэтому `srmod open` переключает секции `Script^{<name>}`
неосновных языков на актуальную нумерацию (`opener.rekey_secondary_langs`):
мост между языками — текст основного языка, `старый ключ -> текст -> новый ключ`,
повторяющиеся тексты раздаются по очереди. Дальше согласие держит гейт сборки
`build.check_secondary_lang_keys`: перевод, ссылающийся на ключ вне таблицы
этой сборки, теперь роняет `srmod build` с инструкцией, а не уезжает к игрокам
молча.

**Факт корпуса (2026-08-28):** ни у одного из 551 мода во втором языке блока
`Script` нет вообще — переводят только UI-строки. То есть механика написана «на
вперёд» и проверена юнит-тестом на синтетике (перекей + оба исхода гейта),
живых случаев в корпусе нет.

  упаковщик у авторов) — такие остаются бинарниками, это штатно.
